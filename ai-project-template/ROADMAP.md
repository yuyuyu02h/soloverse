# ROADMAP.md

## Purpose

SoloVerseを、現在の「動作する個人向けプロトタイプ」から、壊れにくく、分かりやすく、AI住人との継続利用に価値があるプロダクトへ進化させるための実装順です。

このロードマップは、現在のコード、テスト、設定、README、改善記録、Git履歴（現時点では初回コミット1件）から作成しています。プロダクトオーナーの判断が必要な箇所は`[TODO]`としています。

## Current Direction

- 一般公開・商用の完全ローンチは当面目標にしない。
- プロジェクトオーナーが個人制作として使い、作品として満足できる品質を優先する。
- 投稿密度、意味の通る会話、住人らしさ、見た目の完成度を主要な評価軸にする。
- 無料クラウドLLM枠を基本とし、ローカルLLMや有料APIを前提にしない。
- 公開専用の機能は条件付き将来項目とするが、秘密情報、DB、利用者分離の基本安全性は省略しない。

## Current Baseline

現在動作している主な機能:

- 登録、ログイン、30日JWTセッション
- 4ステップのオンボーディング
- 利用者ごとのAI住人と世界設定
- 投稿、入れ子返信、いいね、通知、トレンド
- 遅延リアクション、自律投稿、住人増加、不在反応
- Groq → Gemini → OpenRouterフォールバック
- アカウントと利用者投稿を残したAI世界の再生成
- 一時DB・模擬LLMを使うバックエンドテスト15件
- フロントエンドの型検査と本番ビルド

現在の位置づけ:

- 個人利用・プロトタイプ向け
- SQLiteと単一のバックグラウンドジョブ実行プロセスを前提
- 30秒ポーリング
- 公開サービスに必要な認証、プライバシー、モデレーション、監視、復旧は未完成

## Roadmap Principles

1. ローカルLLMは追加しない。
2. 無料枠を優先し、LLM呼び出し回数と失敗時の消費を測定する。
3. 利用者ごとの`user_id`分離を最重要の不変条件とする。
4. 既存DBを削除しなくても更新できるようにする。
5. 新機能より先に、データ消失・重複実行・認証・復旧のリスクを下げる。
6. AIらしさより、会話の一貫性、具体性、反応の納得感を優先する。
7. 一般公開向け要件は公開方針が変わったときに再評価する。
8. Step番号は依存関係と推奨順を示すが、個人制作の体験改善に必要なStep 3・4は基盤作業と並行できる。

## Priority and Size

| Label | Meaning |
|---|---|
| P0 | 次の機能開発より先に必要 |
| P1 | 初期ベータの品質に必要 |
| P2 | 利用継続と差別化に有効 |
| P3 | 規模・需要が確認できてから |
| S / M / L / XL | 相対的な実装・検証規模。日数ではない |

## Step 1 — コアの信頼性とデータ整合性

Goal: 長時間動かしても重複・孤児データ・データ消失を起こしにくくする。

### 1.1 Versioned migrations（P0 / L）

- [ ] マイグレーション履歴テーブルと連番ファイルを導入する。
- [ ] 現在の起動時テーブル再構築を、原子的でテスト可能な移行へ置き換える。
- [ ] 空DB、現行DB、旧スキーマDBからの移行テストを追加する。
- [ ] 移行前バックアップ、失敗時ロールバック、復旧方法を文書化する。
- [ ] `posts.reply_to`、キュー、通知、author参照の整合性方針を決める。

### 1.2 Queue correctness（P0 / L）

- [ ] リアクションジョブへ冪等性キーまたはDB一意制約を追加する。
- [ ] ジョブ状態を`pending/running/completed/failed/dead`等で明示する。
- [ ] 複数ワーカーを想定するならclaim/lease方式を導入する。
- [ ] 最大試行後のdead-letter確認・再実行手段を追加する。
- [ ] 投稿や住人削除時に関連ジョブが残らないことをDBとテストで保証する。
- [ ] SIGINT/SIGTERM時に新規ジョブを止め、処理中ジョブを安全に終了する。
- [ ] キュー深度、最古待機時間、失敗数を取得できるようにする。

### 1.3 API and DB performance（P1 / M）

- [ ] タイムライン返信プレビューのN+1クエリを一括取得へ変更する。
- [ ] 実データ量を想定したインデックス・クエリ計画テストを追加する。
- [ ] `since`、`before`、同一秒投稿、深い返信ツリーの境界テストを拡充する。
- [ ] APIレスポンススキーマを定義し、フロントエンドの`any`を減らす。
- [ ] エラーコードをHTTPステータスだけでなく安定した機械可読コードで返す。

### 1.4 Testing depth（P0 / L）

- [ ] 登録・ログインのレート制限、JWT期限、無効ユーザーのテストを追加する。
- [ ] すべてのオブジェクトAPIで他利用者IDを使う負のテストを追加する。
- [ ] 再生成中のAPI失敗、Seed失敗、DB失敗、同時実行をテストする。
- [ ] キューの重複、再試行、dead-letter、削除競合をテストする。
- [ ] フロントエンドのコンポーネントテストを導入する。
- [ ] Playwright等で主要なブラウザE2Eフローを追加する。

### Exit Criteria

- 既存DBを保持した移行が自動テストされる。
- 同じジョブを再実行しても二重投稿・二重通知が発生しない。
- 主要APIに所有者/他利用者テストがある。
- 想定データ量でタイムライン取得時間が許容範囲内に収まる。[TODO: 目標値を決める。]

## Step 4 — AI住人、記憶、会話品質

Goal: 投稿数ではなく「この住人らしい」「前の会話を覚えている」という価値を作る。

### 4.1 Structured resident model（P1 / L）

- [ ] 性格、口調、価値観、好き/苦手、生活リズム、関係性を構造化する。
- [ ] 表示名・username・設定が作品固有名詞の模倣になっていないか検証する。
- [ ] 同一世界内で属性・話し方・反応速度が偏らない生成制約を追加する。
- [ ] 住人ごとの活動時間帯と投稿頻度を持たせる。
- [ ] 住人設定のバージョンを保持し、再生成前後を追跡できるようにする。

### 4.2 Memory and relationship（P1 / XL）

- [ ] 短期記憶: 直近スレッドと最近の発言を整理して渡す。
- [ ] 長期記憶: 利用者の好み、重要発言、約束、よく話す話題を明示的に保存する。
- [ ] 関係性: 親密度ではなく、会話回数、共通話題、最近の接触など説明可能な状態を持つ。
- [ ] 古い記憶の要約、重複排除、削除、利用者による編集/忘却を用意する。
- [ ] まずSQLite FTS等の低コスト手段を検討し、埋め込みAPI追加は効果と費用を測って判断する。

### 4.3 Conversation planning and diversity（P1 / L）

- [ ] 「投稿」「直接回答」「相槌」「質問返し」「住人同士の会話」を用途別プロンプトへ分離する。
- [ ] 投稿前に直近内容との意味的重複、同じ語尾、比喩、感情の偏りを検査する。
- [ ] 質問に結論と理由が含まれることを構造的に検証する。
- [ ] 住人同士の返信グラフを計画してから保存し、不自然な会話順を防ぐ。
- [ ] 世界全体の話題配分、時間帯、イベント、沈黙時間を調整する。
- [ ] 生成失敗時は低品質文を保存せず、自然な再試行またはスキップにする。

### 4.4 Provider routing and quota control（P1 / L）

- [ ] ジョブ種別ごとに必要品質を定義し、安価/高速/高品質モデルを使い分ける。
- [ ] 1ユーザー・1日・ジョブ種別ごとの呼び出し上限を設ける。
- [ ] プロバイダーごとの残量を直接取得できない場合も、呼び出し数・429・推定消費を記録する。
- [ ] クールダウンを必要に応じてDBへ永続化する。
- [ ] 設定済みモデルIDの有効性を起動時または管理画面で検査する。
- [ ] 同じ日本語評価セットでモデル別の有効出力率・一貫性を比較し、失敗率が高いモデルを一定時間自動降格する。
- [ ] 全プロバイダー停止時に、UIへ待機理由と再試行見込みを表示する。

### 4.5 Evaluation and user feedback（P0 for AI changes / L）

- [ ] 日本語の質問、呼びかけ、雑談、愚痴、作品ファン会話のgolden datasetを作る。
- [ ] 具体性、一貫性、返信適合性、重複、なりきり逸脱、安全性を自動評価する。
- [ ] 実モデルを使う評価と、完全オフラインの回帰テストを分離する。
- [ ] 「良い反応／違う」「この住人を減らす」「返信を作り直す」フィードバックを追加する。
- [ ] フィードバックをプロンプト改善へ使う場合のプライバシーと保存方針を決める。

### 4.6 Free-first content volume（P0 / L）

- [ ] プロバイダーの残りリクエスト・トークンとリセット目安をレスポンスヘッダーから記録する。
- [ ] 初期投稿・自律投稿で無効項目を捨てたあと、目標件数まで不足分だけ補充する。
- [ ] 1回のLLM呼び出しで半日〜1日分の候補投稿をまとめて生成し、DBキューから時間差で公開する方式を検証する。
- [ ] ユーザーへの返信を最優先、自律投稿を次点、低価値な背景投稿を最後にする日次クォータ配分を追加する。
- [ ] 時刻、天気ではない日常、挨拶など一部の背景投稿を、十分な組み合わせを持つ非LLMテンプレートで生成する案を評価する。
- [ ] 話題適合、具体性、住人らしさ、直近との意味的重複を採点し、低品質な候補を保存しない。
- [ ] バックエンド停止中は自律生成も停止することをUIとREADMEで明示する。
- [ ] 最新の無料枠と運用案は`docs/LLM_FREE_TIER.md`で管理する。

### Exit Criteria

- 同じ住人が複数日にわたり一貫した好みと話し方を示す。
- 質問回答、重複、なりきり逸脱、安全性を定量評価できる。
- LLM利用量と失敗率をユーザー/ジョブ/プロバイダー単位で確認できる。
- 利用者が不要な住人・記憶・反応を制御できる。
