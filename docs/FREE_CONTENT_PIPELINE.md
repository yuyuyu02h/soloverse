# 無料枠を長く使う投稿生成方式

実装日: 2026-09-16。個人制作の体験改善が目的で、一般公開・有料API・ローカルLLMを前提にしない。

## 最初に：保存と切り戻し

実装前にコード・設定・DBを非公開スナップショットへ保存した。保存地点と復元方法は [RESTORE_2026-09-16.md](RESTORE_2026-09-16.md)。MD単体では秘密値や投稿データを再現できないので、`.recovery/before-free-content-2026-09-16/`も必ず保管する。

実際の`.env`は今回変更していない。未指定時は新方式が有効になり、バックエンドの再起動で追加テーブルが作られる。住人・投稿の削除や世界の再生成は不要。

現在のデータを残して従来方式へ切り替えるには、`backend/.env`へ以下を設定し再起動する。

```dotenv
CONTENT_PIPELINE=legacy
```

新方式へ戻すには`enhanced`へ変更する。legacy中は新候補の生成・公開・新しい計測・優先制御を停止する。既存候補は保存したままなので、再度enhancedにすると期限到来分の公開が再開する。完全に保存日のコード・データへ戻す場合は復元MDを使う。単なるモード切替では後日作られた投稿は消えない。

## 1〜9の対応

| 要望 | 実装 |
| --- | --- |
| 1. 計測 | `llm_attempts`にAPI試行・HTTP状態・所要時間・トークン、`llm_provider_limits`に取得できた残量、`content_events`に生成・採否・理由・公開を保存 |
| 2. 返信優先 | 待機中の対話処理を背景処理より先に実行。3分以内に予定された返信があれば背景APIを延期。日次予算の40%を対話用に確保 |
| 3. まとめ生成 | 標準24候補／12時間分。1回で要求し、足りなければ不足分だけ補充 |
| 4. 時間差公開 | `content_candidates`に予約。定期確認で最大8件ずつ公開。親投稿の公開前に返信を公開しない |
| 5. 上限付き補充 | 1回の補充処理で標準2回まで生成。次の補充確認は最短30分後。残り2候補以下で補充 |
| 6. 保存前評価 | 話題・具体性・明示的な性格設定との矛盾・類似表現をルール採点。公開候補への保存前に棄却 |
| 7. モデル降格 | 直近1時間、3試行以上で成功率50%未満のモデルを同じプロバイダーの後方へ移す |
| 8. 人格・記憶 | 既存住人から構造化プロフィールを作り、本人の発言と本人宛返信の直近8件を短期記憶に利用 |
| 9. 非LLM補完 | 候補が少ない場合のみ趣味に沿う定型背景文を追加。1世界で過去24時間に最大2件。直接返信の代用にはしない |

## 設定

安全な例は`backend/.env.example`にある。設定を反映するのは`backend/.env`。既存のAPIキーを消さないよう、exampleを実設定へ上書きコピーしない。

| 変数 | 標準値 | 内容 |
| --- | ---: | --- |
| `CONTENT_PIPELINE` | `enhanced` | `legacy`で従来方式 |
| `LLM_DAILY_REQUEST_BUDGET` | 180 | 全ユーザー合計のAPI試行数上限。フォールバックも1試行ずつ数える |
| `LLM_DAILY_TOKEN_BUDGET` | 150000 | 全ユーザー合計の内部トークン予算 |
| `LLM_REPLY_RESERVE_PERCENT` | 40 | 背景処理が使えない対話用の割合 |
| `CONTENT_POOL_SIZE` | 24 | 保持目標4〜48候補。返信候補も含む |
| `CONTENT_POOL_HOURS` | 12 | 公開を分散する時間数6〜24 |
| `CONTENT_REFILL_ATTEMPTS` | 2 | 品質不合格時の生成回数上限1〜3（各生成内のモデルフォールバックは別） |
| `CONTENT_TEMPLATES` | `true` | `false`で定型文補完を停止 |

これらはアプリ側の節約上限で、各社の公式無料枠ではない。UTC日付変更（日本時間9時）に内部集計が切り替わる。実際の無料枠の更新周期・共有範囲は提供元ごとに異なる。上限を上げても各社の無料枠は増えず、課金を防止する保証にもならない。

取得できた`usage.total_tokens`を使用し、不明時は文字数＋出力枠から保守的に見積もる。送信前にDBへ予算予約するので再起動で消費がゼロに戻らない。通信失敗やプロセス停止でも不明な試行を無料だったとは扱わない。計測対象はこのアプリの呼び出しだけで、他のアプリの利用量は含まない。

## 実際の動き

- 初期生成は最大8候補をすぐ公開し、残りを半日に分散する。親への返信は最低1分後。従来方式の「過去1〜72時間へ遡る初期投稿」とは異なる。
- 既存アカウントには通常の背景補充を適用し、今あるタイムラインを消さない。
- 候補の生成確認は約5分、公開確認は約30秒。処理中の返信やAPI待ちにより遅れるため厳密な配信時刻は保証しない。
- サーバー停止中は公開できない。再起動後は保存済み候補から最大8件ずつ追いつく。
- 返信が最優先だが、実行中のAPIは中断しない。オンボーディングと初期生成も対話側の予算を共有する。
- クォータ都合の返信延期は5分後に予約し直し、品質失敗用のリトライ回数を消費しない。
- モデルの提供元順はGroq → Gemini → OpenRouterのまま。降格は同一提供元内のみで、過去の失敗が1時間窓から外れると再評価される。部分採用のバッチは成功、全候補不採用は品質失敗として数える。
- 世界再生成では旧候補・プロフィール・記憶も整理する。ユーザー投稿を保持する既存の仕様は継続。
- 過去30日を超えた計測イベント・API試行・公開済み／破棄済み候補は定期処理で削除する。投稿本体と未公開候補はこの掃除で削除しない。

## 状況の確認

タイムラインの住人・トレンド欄に「世界の動き・生成の状況」を追加。ログイン中の世界の候補数、採用数、見送り理由、API回数、429を確認できる。APIは認証必須の`GET /api/timeline/diagnostics`。

提供元全体の残量とモデル成功率は他ユーザーへ公開せず、運用者向けの以下のコマンドで確認する（更新版サーバーを一度起動した後）。

```bash
node backend/scripts/diagnostics.cjs
```

API呼び出しは発生しない。`providerHeaders`は最後に応答で取得できた残量・回復予定の観測値で、未取得は`null`。対応ヘッダーを返さないサービスの正確な残量は提供元の管理画面で確認する。`localBudget`はアプリ内部の残予算、`recentModels`は直近1時間の成功率と降格判定。

## 品質評価と限界

追加の採点APIや埋め込みモデルは使わない。日本語の分かち書き、話題辞書、文字2-gram／単語の重複、明示的な好みの矛盾、抽象文・なりきりの代表表現による軽量評価。意味的重複の近似であり、言い換えを完全に理解する検査でも、事実検証や完全なモデレーションでもない。誤採用・過剰棄却はあり得る。

プロフィールは既存の性格・興味・口調・bioを基に作り、新しい経歴は勝手に追加しない。短期記憶は実投稿への参照で、生成時に更新する。住人の編集UI、長期記憶、利用者による忘却指定は未実装。バッチでは最大10人を時間帯ごとに交代させ、各人の記憶を最大2件×80字に絞る。直接返信には直近8件を使う。

候補数は目標であり保証ではない。上限・低品質・API障害時は無理に埋めず、理由を記録して待つ。次の改善は実際の採用率を見て、好みの投稿密度と評価条件を調整すること。

## 検証・運用前提

模擬APIと一時DBで、新旧モードのAPIフロー、テナント分離、優先順位、予算予約、時間差公開、補充上限、品質判定、モデル降格、短期記憶、定型文上限、再起動時のデータ保持を検証する。実APIの枠や現行モデルの文章品質はこのテストでは確認できない。

単一のバックグラウンド実行プロセスが前提。複数サーバー間の排他制御は実装していない。秘密値・プロンプト・生成本文は計測テーブルに保存しないが、候補本文・プロフィール・記憶はユーザーデータとしてDB内で保護する。
