# 2026-09-16 改善前の復元地点

この文書を将来のAI担当者へ「このMDに従って復元して」と渡してください。

## 必要なもの

保存・復元スクリプトはNode.js、Git、tarを利用し、DB保存時にはsqlite3コマンドも必要。設定解析にはバックエンドの既存依存dotenvを使う。保存フォルダーは権限を制限するが暗号化はしていない。

## 保存対象

- 改善前コード: Git commit `c7c23c2eccb7036b8645b9be433646fda6dcb8fb`。
- 個人用スナップショット: `.recovery/before-free-content-2026-09-16/`。
- `source.tar`: コミット内の全ファイル。`history.bundle`: Git履歴の独立コピー。
- `working.patch` / `untracked.tar`: 保存時の未コミット・未追跡ファイル（ある場合）。
- `backend.env` / `frontend.env`: 存在した設定ファイルの非公開コピー。
- `soloverse.db`: SQLiteのオンラインバックアップ機能で整合性を保って保存したDB。
- `manifest.json`: コミット、保存時刻、Nodeバージョン、DB有無、各ファイルのSHA-256。

このフォルダーには秘密情報と個人データを含むため、Gitへ追加・Push・チャットへの出力は禁止。安全な個人バックアップ先にも保管すること。MDだけで秘密値とDB内容を復元することはできないため、このフォルダーも必要。

## まず行う簡単な切り戻し

新方式の実装後は `backend/.env` の `CONTENT_PIPELINE=legacy` を設定して再起動する。既存投稿を保持したまま従来の生成・返信方式に切り替わり、新しい未公開候補の配信は止まる。これは改善前のデータ状態へ巻き戻す操作ではない。

## 保存時点の完全なローカル状態へ戻す手順

新しい空の場所に戻す専用スクリプト（既存のディレクトリを指定すると停止）:

```bash
node backend/scripts/restore.cjs .recovery/before-free-content-2026-09-16 .recovery/restored-original
```

このスクリプトはチェックサム検証・展開・設定とDBのコピーまで実行する。依存インストールと起動は行わない。

1. 現在のバックエンドを停止し、現在の状態も別名でスナップショット保存する。復元で後日の投稿を失わないよう、現在のプロジェクトは上書きしない。
2. 保存フォルダーのmanifest記載のSHA-256を全ファイルについて確認する。欠落・不一致なら復元を止める。
3. 新しい空の復元先ディレクトリを作り、`source.tar`を展開する。必要なら`history.bundle`からGit履歴を復元する。
4. `working.patch`が空でなければ内容を確認して適用し、`untracked.tar`が存在すれば展開する。
5. `backend.env`を復元先の`backend/.env`、`frontend.env`を`frontend/.env.local`へコピーする。秘密値を画面へ表示しない。
6. `soloverse.db`を復元先`backend/soloverse.db`へコピーする。復元先プロセスに元DBの絶対パスを使わせないため、`DB_PATH`は復元先の絶対パスで起動時に上書きする。
7. manifestのNodeバージョンを参考に、両package-lock.jsonを用いて`npm ci`する。依存取得にはネット接続が必要。
8. 既存のローカルサーバーとのポート競合を避けて起動し、登録済みのアカウント・投稿・住人が表示されることを確認する。実API生成は利用枠を消費する。
9. 復元先を使うと決めた後も元フォルダーとスナップショットは残す。`git reset --hard`やDB削除で復元しない。

## 復元検証の記録

今回、チェックサムを検証して別フォルダーに展開し、保存前の追跡コードとの一致とSQLiteの整合性を確認した。保存時の未コミット差分が復元先へ適用されることも確認した。復元検証コピーは非公開の`.recovery/`内にあり、現在のプロジェクトを置き換えていない。

## 再現できる範囲

コード、保存時点のDB、設定ファイル、ロックファイルを復元できる。外部APIの提供モデル・将来の生成文章・失効したAPIキー・ブラウザのログイン状態までは固定できない。シェルで設定した`DB_PATH`を使っていた場合は、スナップショットにも同じ`DB_PATH`を渡すこと。

## 今回の方針

一般公開を急がず個人制作の体験品質を高める。改善前の生成コードを残し、新方式は別サービスと追加テーブルにまとめる。通常の切り戻しではDBを削除しない。
